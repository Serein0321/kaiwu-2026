# 奖励设计超详细解析

本文档专门解释本项目里的奖励设计。目标是把奖励从配置、计算、动作触发、时间衰减、训练样本对齐，到最终进入 PPO 的全过程讲清楚。

相关核心文件：

- `conf/conf.py`：奖励权重和大量奖励阈值常量。
- `feature/reward_manager.py`：奖励计算主逻辑，核心类是 `GameRewardManager`。
- `workflow/train_workflow.py`：每帧何时调用奖励计算，以及如何把 reward 放进 observation。
- `feature/definition.py`：如何把每帧 reward 对齐到上一帧动作，并用 GAE 生成训练目标。
- `feature/evaluation_metrics.py`：用奖励子项统计训练和评估指标。

## 1. 一句话总览

当前奖励系统是一个“基础状态差分奖励 + 战术动作即时奖励”的组合。

它不是只看输赢，也不是只看击杀，而是每帧计算很多细粒度指标：

- 血量差变化。
- 防御塔血量差变化。
- 金钱差变化。
- 经验差变化。
- 法力值变化。
- 死亡和击杀计数变化。
- 补刀事件。
- 前期站位约束。
- 狂暴使用。
- 清线。
- 推线。
- 河蟹争夺。
- 英雄连招。
- 技能释放时机。
- 英雄优先攻击。
- 攻击间距。
- 攻击准确率。
- 草丛伏击。
- 塔下安全。
- 点塔窗口。
- 回复和回城。
- 血包恢复。
- 敌方鲁班大招规避。

最终每个奖励子项都会变成：

```text
子项原始值 origin
  -> 乘子项权重 weight
  -> 乘时间衰减 time_scale
  -> 得到子项加权值 xxx_weight
```

所有子项加权值相加得到：

```text
reward_sum
```

这个 `reward_sum` 会进入训练样本，之后由 `FrameCollector` 计算 GAE，生成：

- `advantage`：给 PPO policy loss 使用。
- `reward_sum` 的累计版本：给 value loss 使用。

## 2. 奖励系统入口

### 2.1 Agent 里初始化 RewardManager

每局开始时，`Agent.reset()` 会创建奖励管理器：

```python
self.reward_manager = GameRewardManager(self.player_id, self.hero_camp)
```

两个关键参数：

| 参数 | 含义 |
|---|---|
| `main_hero_runtime_id` | 当前智能体控制的英雄 id，用于识别“我方英雄” |
| `main_hero_camp` | 当前智能体所在阵营，用于区分我方和敌方 |

奖励管理器内部会维护：

- 我方各奖励项的上一帧值和当前帧值。
- 敌方各奖励项的上一帧值和当前帧值。
- 上一次血包相关事实。
- 上一次敌方鲁班大招相关事实。
- 攻击命中窗口。
- 连续空攻击计数。

### 2.2 训练流程里何时算奖励

`workflow/train_workflow.py` 中每次环境推进后都会计算奖励：

```python
reward = agent.reward_manager.result(
    agent_obs["frame_state"],
    last_action=getattr(agent, "last_action", None),
)
agent_obs["reward"] = reward
```

这里传入两个东西：

| 输入 | 含义 |
|---|---|
| `frame_state` | 环境推进后的新一帧状态 |
| `last_action` | 智能体刚刚执行的动作 |

所以奖励的语义是：

```text
上一帧执行了 last_action
环境推进到当前帧
根据当前帧状态变化和 last_action 计算 reward
```

这点对理解“动作奖励如何对齐”非常重要。

### 2.3 RewardManager 的总入口

奖励总入口：

```python
def result(self, frame_data, last_action=None):
    self.frame_data_process(frame_data)
    self.get_reward(frame_data, self.m_reward_value, last_action=last_action)
    return self.m_reward_value
```

分两步：

1. `frame_data_process(frame_data)`：更新我方和敌方各基础奖励项的当前帧值。
2. `get_reward(...)`：把当前帧值和上一帧值做差，乘权重和时间衰减，加上战术奖励，得到最终 reward 字典。

## 3. 奖励字典长什么样

每次 `GameRewardManager.result()` 返回一个字典。它包含：

- 每个基础奖励项的原始值：`xxx_origin`。
- 每个基础奖励项的加权值：`xxx_weight`。
- 每个战术奖励项的原始值：`xxx_origin`。
- 每个战术奖励项的加权值：`xxx_weight`。
- 总奖励：`reward_sum`。

例如：

```text
hp_point_origin
hp_point_weight
tower_hp_point_origin
tower_hp_point_weight
...
skill_urgency_origin
skill_urgency_weight
...
reward_sum
```

其中：

```text
xxx_weight = xxx_origin * 子项权重 * time_scale
```

最终：

```text
reward_sum = 所有 xxx_weight 之和
```

注意：

- 代码里有 `weight_sum` 变量，但没有用于归一化。
- 所以 `reward_sum` 是直接相加，不会除以总权重。

## 5. 时间衰减

所有奖励默认都会乘时间衰减：

```python
time_scale = math.pow(0.6, frame_no / GameConfig.TIME_SCALE_ARG)
```

当前：

```python
TIME_SCALE_ARG = 8000
```

所以：

| 帧号 | time_scale |
|---:|---:|
| 0 | 1.0 |
| 1000 | 0.9381 |
| 4000 | 0.7746 |
| 8000 | 0.6 |
| 16000 | 0.36 |

含义：

- 越早发生的奖励权重越大。
- 越晚发生的奖励权重越小。
- 8000 帧时衰减到 0.6 倍。
- 16000 帧时衰减到 0.36 倍。

`REWARD_WITHOUT_TIME_SCALE` 当前是空集合，因为里面的项都被注释掉了：

```python
REWARD_WITHOUT_TIME_SCALE = {
    # "hp_point",
    # "tower_hp_point",
    # "death",
    # "kill",
}
```

所以按当前代码，所有基础奖励和所有战术奖励都会被时间衰减。

## 6. 基础奖励的计算框架

基础奖励的核心思想是：

```text
先分别计算我方当前帧指标和敌方当前帧指标
再计算差分
再乘权重
```

内部有三张 map：

| map | 作用 |
|---|---|
| `m_main_calc_frame_map` | 保存我方每个基础奖励项的上一帧值、当前帧值 |
| `m_enemy_calc_frame_map` | 保存敌方每个基础奖励项的上一帧值、当前帧值 |
| `m_cur_calc_frame_map` | 保存最终面向我方视角的奖励值 |

每帧先调用：

```python
self.set_cur_calc_frame_vec(self.m_main_calc_frame_map, frame_data, main_camp)
self.set_cur_calc_frame_vec(self.m_enemy_calc_frame_map, frame_data, enemy_camp)
```

每个 reward item 都会先执行：

```python
reward_struct.last_frame_value = reward_struct.cur_frame_value
```

然后根据当前帧状态更新 `cur_frame_value`。

在 `get_reward()` 中，基础奖励大体分三类：

### 6.1 双方差分型

大部分基础奖励使用：

```text
cur = main_cur - enemy_cur
last = main_last - enemy_last
origin = cur - last
```

也就是看“我方相对敌方的优势变化”。

适用项：

- `money`
- `tower_hp_point`
- `death`
- `kill`
- 大部分未特殊处理的项

### 6.2 特殊差分型

有些奖励有特殊逻辑：

- `hp_point`：使用双方血量变换值的差分，但对 last 为 0 的情况做特殊处理。
- `ep_rate`：只看我方蓝量比例变化，不和敌方相减。
- `exp`：看双方经验差分，但满级后置 0。
- `last_hit`：直接使用当前帧事件，不再做跨帧差分。
- `forward`：直接使用当前帧位置值，不做差分。

### 6.3 加权输出

每项最终写入：

```python
reward_dict[reward_name + "_origin"] = reward_struct.value
reward_dict[reward_name + "_weight"] = reward_struct.value * reward_struct.weight * time_scale
```

## 7. 基础奖励逐项详解

### 7.1 `hp_point`：血量优势变化

权重：

```text
2.0
```

单方当前帧值：

```python
sqrt(sqrt(hp / max_hp))
```

数学形式：

```text
hp_score = (hp_rate) ^ 0.25
```

这不是直接用 `hp / max_hp`，而是四次方根。

四次方根的效果：

- 低血时变化更敏感。
- 例如从 0.1 到 0.2 的变化，会比线性比例更显眼。
- 让模型更重视低血区间的生死风险。

奖励计算：

```text
main_hp_score = own_hp_rate ^ 0.25
enemy_hp_score = enemy_hp_rate ^ 0.25
hp_diff = main_hp_score - enemy_hp_score
hp_point_origin = hp_diff_this_frame - hp_diff_last_frame
hp_point_weight = hp_point_origin * 2.0 * time_scale
```

特殊处理：

- 如果双方上一帧血量值都是 0，则当前 reward 置 0。
- 如果我方上一帧是 0，则按 `0 - enemy` 处理。
- 如果敌方上一帧是 0，则按 `main - 0` 处理。

设计意图：

- 打掉敌方血量会让 `enemy_hp_score` 降低，`main - enemy` 上升，得到正奖励。
- 自己掉血会让 `main_hp_score` 降低，`main - enemy` 下降，得到负奖励。
- 击杀或被击杀附近，因为血量接近 0，变化会更明显。

### 7.2 `tower_hp_point`：防御塔血量优势变化

权重：

```text
10.0
```

单方当前帧值：

```text
tower_hp_rate = tower_hp / tower_max_hp
```

奖励计算：

```text
tower_diff = own_tower_hp_rate - enemy_tower_hp_rate
tower_hp_point_origin = tower_diff_this_frame - tower_diff_last_frame
tower_hp_point_weight = tower_hp_point_origin * 10.0 * time_scale
```

正负方向：

- 敌方塔掉血：`enemy_tower_hp_rate` 下降，`own - enemy` 上升，正奖励。
- 己方塔掉血：`own_tower_hp_rate` 下降，负奖励。

权重是 10.0，是基础奖励里最大的正权重。

这说明项目非常重视防御塔：

- 推塔收益很高。
- 守塔也很重要。
- 只靠打英雄不够，塔血是核心目标。

### 7.3 `money`：经济优势变化

权重：

```text
0.004
```

单方当前帧值：

```python
moneyCnt / money_cnt / money
```

奖励计算：

```text
money_diff = own_money - enemy_money
money_origin = money_diff_this_frame - money_diff_last_frame
money_weight = money_origin * 0.004 * time_scale
```

因为金币数值通常比较大，所以权重很小。

举例：

```text
如果这一段我方比敌方多赚 50 金币：
origin = 50
weight = 50 * 0.004 = 0.2
```

设计意图：

- 鼓励补兵、击杀、吃资源带来的经济领先。
- 但不让金币奖励压过塔血和血量奖励。

### 7.4 `exp`：经验优势变化

权重：

```text
0.004
```

单方当前帧值由 `calculate_exp_sum()` 计算。

它不是只用当前等级内经验，而是把历史升级所需经验累加：

```python
for i in range(1, level):
    exp_sum += max_exp_of_level[i]
exp_sum += current_exp
```

这样得到的是“累计经验”。

奖励计算：

```text
exp_diff = own_exp_sum - enemy_exp_sum
exp_origin = exp_diff_this_frame - exp_diff_last_frame
exp_weight = exp_origin * 0.004 * time_scale
```

特殊处理：

```python
if main_hero and main_hero["level"] >= 15:
    reward_struct.value = 0
```

也就是说，主英雄满级后不再给经验奖励。

设计意图：

- 鼓励经验领先。
- 鼓励吃兵线和资源。
- 满级后经验不再有价值，所以奖励置 0。

### 7.5 `ep_rate`：蓝量比例变化

权重：

```text
0.75
```

单方当前帧值：

```text
ep_rate = ep / max_ep
```

如果英雄死亡或 `max_ep=0`，当前值为 0。

奖励计算只看我方：

```text
ep_rate_origin = own_ep_rate_this_frame - own_ep_rate_last_frame
```

特殊处理：

```python
if last_frame_value > 0:
    value = cur - last
else:
    value = 0
```

这避免第一帧或无蓝英雄带来异常奖励。

设计意图：

- 蓝量恢复是正奖励。
- 技能消耗蓝量可能带来负奖励。
- 它可能在一定程度上抑制无意义乱放技能。

注意：

- 它不比较敌方蓝量。
- 它只看自己蓝量变化。
- 如果技能带来的战斗收益足够大，其他奖励可以抵消蓝量消耗的负向影响。

### 7.6 `death`：死亡计数差分

权重：

```text
-1.0
```

单方当前帧值：

```python
deadCnt / dead_cnt
```

奖励计算：

```text
death_diff = own_dead_count - enemy_dead_count
death_origin = death_diff_this_frame - death_diff_last_frame
death_weight = death_origin * (-1.0) * time_scale
```

正负方向：

- 我方死亡一次：`own_dead_count` 增加，`death_origin > 0`，乘 `-1.0` 后是负奖励。
- 敌方死亡一次：`enemy_dead_count` 增加，`death_origin < 0`，乘 `-1.0` 后是正奖励。

这是标准的“少死、多让敌人死”奖励。

### 7.7 `kill`：击杀计数差分

权重：

```text
-0.6
```

单方当前帧值：

```python
killCnt / kill_cnt
```

奖励计算按通用差分：

```text
kill_diff = own_kill_count - enemy_kill_count
kill_origin = kill_diff_this_frame - kill_diff_last_frame
kill_weight = kill_origin * (-0.6) * time_scale
```

按代码字面行为：

- 如果 `own_kill_count` 增加，`kill_origin > 0`，乘 `-0.6` 后是负奖励。
- 如果 `enemy_kill_count` 增加，`kill_origin < 0`，乘 `-0.6` 后是正奖励。

这和通常理解的“击杀奖励应为正”相反。

因此这里必须特别注意：

- 可能是协议里的 `killCnt` 语义并不是普通击杀数。
- 也可能是继承模板时保留了一个需要重新确认的权重符号。
- 本文档只描述当前代码真实行为，不假设它一定是设计者本意。

如果后续训练表现异常，比如模型不愿意击杀或击杀后 reward 反而下降，应优先检查这个奖励项。

### 7.8 `last_hit`：补刀事件

权重：

```text
0.5
```

当前帧值从 `frame_action["dead_action"]` 里计算。

逻辑：

```python
if killer == main_hero and death is soldier:
    cur_frame_value += 1.0
elif killer == enemy_hero and death is soldier:
    cur_frame_value -= 1.0
```

`last_hit` 不做跨帧差分，而是直接使用当前帧事件值：

```text
last_hit_origin = 当前帧补刀事件值
last_hit_weight = last_hit_origin * 0.5 * time_scale
```

正负方向：

- 我方补到小兵：正奖励。
- 敌方补到小兵：负奖励。

设计意图：

- 明确鼓励最后一击。
- 弥补仅靠 `money` 和 `exp` 不够直接的问题。

### 7.9 `forward`：前期站位约束

权重：

```text
0.01
```

截止帧：

```python
REMOVE_FORWARD_AFTER = 1000
```

也就是说超过 1000 帧后该项为 0。

计算：

```python
dist_hero2emy = distance(hero, enemy_tower)
dist_main2emy = distance(own_tower, enemy_tower)

if hero_hp_rate > 0.99 and dist_hero2emy > dist_main2emy:
    forward_value = (dist_main2emy - dist_hero2emy) / dist_main2emy
else:
    forward_value = 0
```

注意这个公式：

- 当英雄比己方塔还更远离敌方塔时，`dist_hero2emy > dist_main2emy`。
- 此时 `(dist_main2emy - dist_hero2emy)` 是负数。
- 所以 `forward_value` 是负奖励。

因此按当前代码，这个项更像是：

```text
满血前期不要缩在己方塔后太远
```

它并不是一个“越往前越正”的奖励。大部分正常位于两塔之间的位置，`forward_value` 为 0。

## 8. 战术奖励计算框架

战术奖励由：

设计意图：

- 让模型在可安全换血时别把攻击浪费在小兵上。

### 9.6 `attack_spacing`：普攻距离控制

权重：

```text
0.22
```

触发：

```python
if button == NORMAL_ATTACK_BUTTON and target == 1 and enemy_hp > 0:
    attack_spacing = -1.0 if tower_aggro_risk else attack_spacing_score(enemy_distance, self_attack_range)
```

如果攻击敌方英雄会有塔仇恨风险，直接给 `-1.0`。

否则根据距离算分：

```python
ratio = enemy_distance / attack_range
safe_ratio = 0.65
ideal_ratio = 0.90
```

规则：

| 距离比例 | 分数 |
|---|---:|
| 大于攻击范围 | 0.0 |
| `ratio >= 0.90` | 1.0 |
| `0.65 <= ratio < 0.90` | 从 0 线性增加到 1 |
| `ratio < 0.65` | 负分，最低 -1 |

直观理解：

- 最理想是站在攻击范围的 90% 附近或更远一点。
- 太近容易被反打，所以给负分。
- 太远打不到人，给 0。

设计意图：

- 鼓励射手保持攻击距离。
- 对鲁班和狄仁杰这种远程英雄尤其重要。

权重：

```text
0.35
```

这是战术奖励中权重很高的一项。

触发前提：

```python

```

其中：



也就是：

- 鲁班七号：优先三技能，再一技能，再二技能。
- 狄仁杰：优先三技能，再一技能。

奖励规则：

| 行为 | 原始奖励 |
|---|---:|
| 有塔仇恨风险 | -1.0 |
| 使用最高优先级技能打敌方英雄，且技能是 3 技能 | +1.4 |
| 使用最高优先级技能打敌方英雄，非 3 技能 | +1.0 |

| 选择无动作/移动，或技能打错目标 | -0.5 |

设计意图：

- 敌人在技能范围内时，优先鼓励使用关键技能。
- 3 技能通常是强先手或关键技能，所以额外给高奖励。
- 不鼓励窗口出现时还保守普攻或乱移动。
- 不鼓励技能打空目标、打自己、打塔、打河蟹等错误目标。

权重：

```text

```

由 `_settle_cake_recovery()` 计算，是一个带历史状态的奖励。

相关阈值：

| 常量 | 数值 | 含义 |
|---|---:|---|
| `CAKE_LOW_HP_THRESHOLD` | 0.35 | 低血阈值 |
| `CAKE_MID_HP_THRESHOLD` | 0.55 | 中血阈值 |
| `CAKE_SEEK_MAX_DISTANCE` | 12000 | 低血寻找血包最大距离 |
| `CAKE_NEAR_DISTANCE` | 1800 | 靠近血包距离 |
| `CAKE_CONSUME_DISTANCE` | 2500 | 认为能吃到血包的距离 |
| `CAKE_HP_GAIN_THRESHOLD` | 0.08 | 判断吃到血包的血量增长阈值 |
| `CAKE_APPROACH_DELTA` | 500 | 判断是否靠近或远离的距离变化 |

#### 9.16.1 成功吃到血包

如果上一帧血包存在，这一帧血包不存在：

```python
if last_facts["cake_available"] and not cake_available:
```

并且：

```text
上一帧距离血包 <= 2500
当前血量比上一帧增加 >= 0.08
```

则认为吃到了血包。

奖励：

| 上一帧血量 | 原始奖励 |
|---|---:|
| `<= 0.35` | +1.8 |
| `<= 0.55` | +1.0 |

#### 9.16.2 低血靠近血包

低血寻找条件：

```text
self_hp <= 0.35
cake_distance <= 12000
```

如果比上一帧靠近至少 500：

```text
+0.3
```

如果比上一帧远离至少 500：

```text
-0.3
```

如果距离血包小于等于 1800：

```text
+0.8
```

#### 9.16.3 中血靠近血包

中血寻找条件：

```text
0.35 < self_hp <= 0.55
cake_distance <= 7000
敌方死亡或距离 > 6500
```

如果靠近至少 500：

```text
+0.15
```

如果距离血包小于等于 1800：

```text
+0.4
```

#### 9.16.4 不该吃血包时不鼓励

如果存在击杀窗口：

```text
enemy_hp <= 0.20
敌方在攻击范围内
self_hp >= 0.45
```

则不进入血包寻路奖励。

也就是说：

- 敌方残血可杀。
- 自己血量健康。
- 就不要为了血包放弃击杀窗口。

#### 9.16.5 低血还乱打的惩罚

如果低血寻血包窗口中，仍然攻击敌方英雄或塔：

```python
if low_hp_seek and is_attack_button and target in [1, 7]:
    reward += -0.5
```

设计意图：

- 低血时应该优先活下来。
- 不鼓励低血硬打英雄或塔。

### 9.17 `enemy_luban_ult_safety`：敌方鲁班大招安全

权重：

```text
0.30
```

由 `_settle_enemy_luban_ult_safety()` 计算，也是带历史状态的奖励。

首先 `_enemy_luban_ult_distance()` 会查找：

- 敌方英雄是否是鲁班七号，`config_id == 112`。
- 子弹是否来自敌方鲁班。
- 子弹 slot 是否是三技能，`SLOT_SKILL_3` 或 `"3"`。

如果找到，取最近距离。

相关常量：

| 常量 | 数值 | 含义 |
|---|---:|---|
| `LUBAN_ULT_DANGER_RADIUS` | 3200 | 危险范围 |
| `LUBAN_ULT_WARNING_RADIUS` | 5400 | 警告范围 |
| `LUBAN_ULT_ESCAPE_DELTA` | 450 | 判断正在远离的距离增量 |
| `LUBAN_ULT_STAY_PENALTY` | -1.0 | 待在危险范围惩罚 |
| `LUBAN_ULT_LOW_HP_EXTRA_PENALTY` | -0.35 | 低血额外惩罚 |
| `LUBAN_ULT_APPROACH_PENALTY` | -0.35 | 向大招靠近惩罚 |
| `LUBAN_ULT_ESCAPE_REWARD` | 0.35 | 远离大招奖励 |
| `LUBAN_ULT_EXIT_REWARD` | 1.0 | 从危险范围离开奖励 |

规则：

| 情况 | 原始奖励 |
|---|---:|
| 在危险范围内，距离 <= 3200 | -1.0 |
| 在危险范围内且低血 | 额外 -0.35 |
| 在警告范围内，并比上一帧远离 >= 450 | +0.35 |
| 在警告范围内，并比上一帧靠近 >= 450 | -0.35 |
| 上一帧在危险范围内，这一帧离开危险范围 | +1.0 |

设计意图：

- 看到敌方鲁班大招后要离开。
- 低血还待在大招里要重罚。
- 朝大招方向靠近要罚。
- 成功脱离危险区要奖。

## 10. 奖励如何和动作对齐

这一节很关键，因为奖励不是在 `predict()` 里立刻写进同一帧动作。

### 10.1 环境推进顺序

训练循环大致是：

```text
当前 observation 已经带有上一动作产生的 reward
  -> agent.predict(observation)，得到当前动作 action_t
  -> build_frame(agent, observation)，保存当前状态、当前动作、当前 value、observation 中的 reward
  -> env.step(action_t)，推进环境
  -> 对新 observation 计算 reward，也就是 action_t 产生的 reward
  -> 下一轮 build_frame 时再把这个 reward 带进样本
```

### 10.2 FrameCollector 的 reward 平移

`FrameCollector.save_frame()` 里有一段非常重要：

```python
if len(self.rl_data_map[agent_id]) > 0:
    last_rl_data_info.next_value = rl_data_info.value
    last_rl_data_info.reward = reward

rl_data_info.reward = 0
self.rl_data_map[agent_id][rl_data_info.frame_no] = rl_data_info
```

含义：

- 当前 frame 中携带的 reward，实际上属于上一帧动作。
- 所以保存当前 frame 时，会把当前 reward 写到上一条样本的 `reward` 字段里。
- 当前 frame 的 reward 先置 0，等待下一帧来填。

因此训练数据中的 `(s_t, a_t, r_t, V(s_{t+1}))` 是对齐的：

```text
上一帧样本:
  feature = s_t
  action = a_t
  reward = 环境执行 a_t 后得到的 r_t
  next_value = V(s_{t+1})
```

这避免了“把 action_t 的奖励错放到 s_{t+1}”的问题。

### 10.3 最后一帧奖励

对局结束时：

```python
frame_collector.save_last_frame(
    reward=self.get_agent_observation(observation, i)["reward"]["reward_sum"],
)
```

`save_last_frame()` 会把最后状态的 reward 写给最后一条已保存样本：

```python
last_rl_data_info.next_value = 0
last_rl_data_info.reward = reward
```

也就是说终止状态的 bootstrap value 为 0。

## 11. 奖励如何进入 GAE

`feature/definition.py` 中 `FrameCollector._calc_reward()` 会把原始逐帧 reward 转成：

- advantage。
- value target，也就是训练里叫 `reward_sum` 的累计值。

核心公式：

```python
delta = -rl_info.value + rl_info.reward + gamma * rl_info.next_value
gae = gae * gamma * lamda + delta
rl_info.advantage = gae
rl_info.reward_sum = gae + rl_info.value
```

数学形式：

```text
delta_t = r_t + gamma * V(s_{t+1}) - V(s_t)
GAE_t = delta_t + gamma * lambda * GAE_{t+1}
value_target_t = GAE_t + V(s_t)
```

当前参数：

```text
gamma = 0.995
lambda = 0.95
```

在进入 GAE 前，单帧 reward 会被裁剪：

```python
reward = clip(reward, -100, 100)
```

也就是：

```text
单帧 reward 被限制在 [-100, 100]
```

当前奖励项权重通常较小，所以正常情况下不容易碰到这个裁剪，但它提供了异常保护。

## 12. reward_sum 如何进入 PPO loss

训练样本中每帧有两个重要值：

| 字段 | 来源 | 用途 |
|---|---|---|
| `reward` | 原始单帧奖励，经对齐后进入 GAE | 计算 advantage 和 value target |
| `advantage` | GAE 输出 | PPO policy loss |
| `reward_sum` | `gae + value` | value loss 的监督目标 |

在 `model/model.py` 中：

```python
self.value_cost = 0.5 * mean((reward_sum - value)^2)
```

policy loss 中：

```python
surr1 = ratio * advantage
surr2 = clipped_ratio * advantage
policy_loss = -mean(min(surr1, surr2))
```

所以奖励设计会通过两条路影响学习：

1. 影响 `advantage`，从而告诉策略“这个动作比预期好还是差”。
2. 影响 `reward_sum/value_target`，从而训练 critic 学会预测局面价值。

## 14. 奖励整体设计意图

### 14.1 基础奖励负责长期方向

基础奖励表达的是“这局游戏真正应该变好”的指标：

- 血量优势。
- 塔血优势。
- 金钱优势。
- 经验优势。
- 死亡差。
- 补刀。

这些奖励和胜负目标更接近，但往往反馈稀疏或延迟。

例如：

- 推塔需要很久才看到塔血变化。
- 经济领先来自很多小动作累积。
- 击杀和死亡不是每帧发生。

### 14.2 战术奖励负责短期动作引导

战术奖励表达的是“当前这个动作是否符合对线常识”：

- 对拼时开狂暴。
- 该放技能时放技能。
- 技能打敌方英雄，不要打错目标。
- 低血先吃血包或回复。
- 不要无兵越塔。
- 有兵扛塔时点塔。
- 鲁班大招里要离开。

这些奖励反馈更密集，能更快塑造行为。

### 14.3 安全奖励优先级很高

最明显的是：

- `tower_safety` 权重 0.45，原始惩罚可到 -2.4。
- `skill_urgency` 遇到塔仇恨风险直接 -1。
- `attack_spacing` 遇到塔仇恨风险直接 -1。
- `combo_luban` 和 `combo_direnjie` 遇到塔仇恨风险 -0.8。
- `cake_recovery` 在低血时攻击英雄或塔会罚。

这说明当前设计很明确：

```text
宁可少打一点，也不要无脑送塔、低血硬打、站进危险范围。
```

### 14.4 英雄专属行为被显式塑形

奖励对 112 和 133 做了不同连招 shaping：

- 鲁班七号鼓励 3 技能/其他技能/普攻的节奏。
- 狄仁杰更强调 3 技能和 1 技能打英雄。

这和观测中的战术上下文特征是一套配合：

- 观测告诉模型当前连招阶段和技能可用性。
- 奖励告诉模型什么连招动作是好的。

## 15. 当前实现中需要特别注意的细节

### 15.1 `kill` 权重方向需要确认

当前代码按字面行为：

```text
kill_origin = Δ(own_kill - enemy_kill)
kill_weight = kill_origin * (-0.6)
```

如果 `killCnt` 真的是普通击杀数，那么这会惩罚自己击杀、奖励敌方击杀。

这很可能不是直觉期望，因此建议训练表现异常时优先检查。

不过本文档不修改代码，只记录当前实现。

### 15.2 `forward` 更像“别满血缩塔后”惩罚

`forward` 名字像前进奖励，但公式只在：

```text
满血
英雄到敌塔距离 > 我方塔到敌塔距离
```

时给负值。

所以它不是正向鼓励前进，而是前 1000 帧惩罚满血躲在己方塔后更远的位置。

### 15.3 所有奖励都会时间衰减

`REWARD_WITHOUT_TIME_SCALE` 当前为空。

因此：

- 塔血奖励衰减。
- 死亡奖励衰减。
- 战术奖励衰减。
- 击杀相关奖励也衰减。

如果希望死亡、推塔这类关键事件不随时间衰减，需要把对应 key 加入 `REWARD_WITHOUT_TIME_SCALE`。

### 15.4 战术奖励使用的是 last_action

战术奖励不是只看当前状态，还看刚刚执行的动作。

例如：

- 刚刚是不是普攻。
- 刚刚是不是用 3 技能。
- 刚刚 target 是不是敌方英雄。
- 刚刚是不是回城。

所以传入 `last_action` 非常关键。如果 `last_action` 丢失，大量战术奖励会变成 0 或无法正确判断。

### 15.5 `safe_recall_window` 要求敌方死亡

当前 safe recall：

```text
lane_cleared and enemy_dead and self_low_hp
```

它不是“敌方很远”也可以，而是要求敌方血量为 0。

这比战术特征里的 safe recall 可能更严格。

### 15.6 `tower_safety` 的优先级会盖过很多进攻奖励

很多进攻相关奖励都显式判断：

- `not tower_aggro_risk`
- `not tower_danger`
- `not no_minion_tower_dive`

这意味着塔下安全是一个高优先级约束。

如果模型看起来塔下很保守，这是奖励设计直接导致的。

### 15.7 `recovery_choice` 非低血也有小正奖励

只要按了回复按钮：

```text
低血且不是安全回城窗口: +1.0
其他情况: +0.2
```

所以它并不会惩罚健康时用回复，只是奖励较小。

如果模型过度使用回复，需要检查这个项和技能合法动作/冷却条件。

### 15.8 `m_init_calc_frame_map` 当前没有实际使用

`GameRewardManager.__init__()` 中有：

```python
self.m_init_calc_frame_map = {}
```

但当前奖励逻辑没有看到后续使用。

这是一个遗留字段或预留字段。

### 15.9 `REWARD_WEIGHT_DICT` 聚合了基础和战术，但 frame map 默认只用基础

`init_calc_frame_map(include_tactic=False)` 默认只使用：

```python
BASE_REWARD_WEIGHT_DICT
```

`GameRewardManager` 初始化三个 map 时都没有传 `include_tactic=True`。

战术奖励是后面单独调用 `calculate_tactic_rewards()` 计算并加入 `reward_dict` 的。

所以：

- `REWARD_WEIGHT_DICT` 是聚合配置。
- 但实际基础 frame map 只含基础奖励。
- 战术奖励不通过 `RewardStruct` 差分系统，而是单独即时计算。

## 16. 如果要调整奖励，应该怎么改

### 16.1 想加强推塔

可调整：

- `tower_hp_point` 权重。
- `tower_push` 权重。
- `lane_push` 权重。

注意：

- 只提高 `tower_push` 会加强“点塔动作”。
- 提高 `tower_hp_point` 会加强“真正打掉塔血”。
- 二者效果不同。

### 16.2 想减少送塔

可调整：

- `tower_safety` 权重。
- `TOWER_AGGRO_RISK_PENALTY`。
- `TOWER_AGGRO_TARGETED_PENALTY`。
- `TOWER_LOW_HP_EXTRA_PENALTY`。

当前塔下惩罚已经较强，如果模型过于保守，不一定要继续加。

### 16.3 想加强击杀欲望

优先检查：

- `kill` 权重方向。
- `hp_point` 是否已经足够鼓励打残敌方。
- `combo_luban`、`combo_direnjie`、`skill_urgency` 是否推动正确输出。
- `tower_safety` 是否过度压制塔下追击。

如果 `killCnt` 的语义确认是普通击杀数，`kill=-0.6` 很值得重新审视。

### 16.4 想加强补刀和发育

可调整：

- `last_hit` 权重。
- `money` 权重。
- `exp` 权重。
- `lane_clear` 权重。

区别：

- `last_hit` 直接奖励最后一击。
- `money` 和 `exp` 奖励经济经验结果。
- `lane_clear` 奖励清兵动作。

### 16.5 想减少乱放技能

可调整：

- `skill_urgency` 惩罚项。
- `ep_rate` 权重。
- `attack_accuracy` 权重。

但要小心：

- `ep_rate` 过高可能让模型舍不得放技能。
- `skill_urgency` 过高可能让模型一有窗口就强行放技能。

### 16.6 想加强血包和续航

可调整：

- `cake_recovery` 权重。
- `CAKE_LOW_*` 和 `CAKE_MID_*` 系列常量。
- `recovery_choice` 权重。
- `safe_recall` 权重。

需要注意：

- 血包奖励里有击杀窗口排除逻辑。
- 过强的血包奖励可能导致模型低血时放弃可杀目标。

```text
每局 reset
  |
  v
Agent 创建 GameRewardManager
  |
  v
每帧 env.step(action) 后得到新 observation
  |
  v
RewardManager.result(frame_state, last_action)
  |
  +--> frame_data_process(frame_state)
  |       |
  |       +--> 找到我方 camp 和敌方 camp
  |       +--> set_cur_calc_frame_vec(main_map, frame_state, main_camp)
  |       +--> set_cur_calc_frame_vec(enemy_map, frame_state, enemy_camp)
  |
  +--> get_reward(frame_state, reward_dict, last_action)
          |
          +--> 对基础奖励逐项计算 origin
          |       |
          |       +--> hp_point
          |       +--> tower_hp_point
          |       +--> money
          |       +--> exp
          |       +--> ep_rate
          |       +--> death
          |       +--> kill
          |       +--> last_hit
          |       +--> forward
          |
          +--> 每项乘 base weight 和 time_scale
          |
          +--> calculate_tactic_rewards(frame_state, last_action)
          |       |
          |       +--> 收集英雄、小兵、塔、河蟹、血包、子弹事实
          |       +--> 解析 last_action 的 button 和 target
          |       +--> 计算 17 个战术奖励
          |
          +--> 每项乘 tactic weight 和 time_scale
          |
          +--> reward_sum = 所有加权项之和
```

进入训练：

```text
observation["reward"]["reward_sum"]
  |
  v
build_frame()
  |
  v
FrameCollector.save_frame()
  |
  +--> 把当前 observation 携带的 reward 写给上一帧样本
  +--> 设置上一帧 next_value = 当前 value
  |
  v
FrameCollector._calc_reward()
  |
  +--> GAE
  +--> advantage
  +--> value target
  |
  v
PPO learn()
```

## 18. 最终总结

当前奖励设计可以概括成：

```text
基础奖励负责大方向：
血量、塔血、经济、经验、死亡、补刀、前期站位。

战术奖励负责动作塑形：
技能、连招、目标选择、塔下安全、河蟹、血包、回城、鲁班大招规避。

时间衰减负责节奏：
越早建立优势，奖励越大。

FrameCollector 负责动作奖励对齐：
当前 observation 中的 reward 会写给上一帧动作。

GAE 负责把单帧 reward 变成 PPO 可用的 advantage 和 value target。
```

最关键的三条主线：

1. `reward_sum = sum(origin * weight * time_scale)`，不做权重归一化。
2. 基础奖励多是“我方相对敌方的状态差分”，战术奖励多是“last_action 触发的即时 shaping”。
3. 奖励不会直接训练策略，而是先经过 FrameCollector 对齐，再经过 GAE，最后进入 PPO loss。

最值得注意的三个实现细节：

1. `kill` 权重当前为 `-0.6`，按代码字面行为可能和常规击杀奖励方向相反，需要确认协议语义。
2. `forward` 实际更像前 1000 帧“满血不要缩在塔后”的惩罚，而不是正向推进奖励。
3. 所有奖励当前都会时间衰减，因为 `REWARD_WITHOUT_TIME_SCALE` 实际为空。
