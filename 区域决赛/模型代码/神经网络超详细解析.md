# 神经网络超详细解析

本文档专门解释本项目里的神经网络。目标不是泛泛介绍 PPO，而是把当前代码中真实存在的网络结构、输入输出、张量形状、动作头、target 头、LSTM、采样、训练损失和容易混淆的细节逐项讲清楚。

相关核心文件：

- `model/model.py`：神经网络本体，包含 `Model`、`MLP`、`make_fc_layer`、`compute_loss`。
- `conf/conf.py`：所有输入维度、动作空间、LSTM 配置、PPO 超参数。
- `feature/obs_builder.py`：把游戏状态构造成 4078 维观测向量。
- `feature/tactic_context.py`：生成 143 维战术上下文特征。
- `agent.py`：模型推理、合法动作 mask、动作采样、LSTM 状态维护。
- `algorithm/algorithm.py`：训练入口，调用模型前向和 loss。
- `feature/definition.py`：帧样本构造、GAE、16 帧 LSTM 样本打包。
- `战术上下文特征说明.md`：已有的战术特征专门说明。

## 1. 一句话总览

这个项目里的神经网络是一个用于 MOBA 1v1 对线智能体的 PPO Actor-Critic 网络。

它的特点是：

- 输入不是图像，而是手工构造好的结构化向量。
- 每帧观测总维度是 4078。
- 其中 3935 维是实体特征，143 维是战术上下文特征。
- 实体特征会按英雄、小兵、河蟹、防御塔、子弹拆开，各自进入小 MLP 编码。
- 编码后的实体拼成 480 维局面向量。
- 480 维局面向量走两路：
  - 一路进 LSTM，学习时间依赖。
  - 一路进普通 MLP，保留当前帧即时判断。
- 战术上下文特征单独走 MLP。
- 最后三路拼起来变成 1088 维，再压成 512 维公共表示。
- Actor 输出 6 个动作分支的 logits，总共 85 维。
- Critic 输出 1 个 value，表示当前局面的价值估计。
- 训练使用 PPO clipped loss，加 value loss，熵项当前配置下权重为 0。

从形状上看，主干可以概括为：

```text
feature_vec: 4078
  -> entity_vec: 3935
  -> tactic_vec: 143

entity_vec
  -> hero / soldier / crab / organ / bullet encoders
  -> concat_result: 480

concat_result
  -> concat_mlp: 480 -> 512
  -> LSTM: 512 -> 512

concat_result
  -> concate_mlp_other: 480 -> 512 -> 512

tactic_vec
  -> tactic_mlp: 143 -> 128 -> 64

[LSTM 512, MLP bypass 512, tactic 64]
  -> concat: 1088
  -> lstm_and_linear_mlp: 1088 -> 512

公共 512
  -> 5 个普通动作头: 12 + 16 + 16 + 16 + 16
  -> 1 个 target 动作头: 9
  -> value head: 1
```

## 2. 关键符号

后文用这些符号描述张量形状：

| 符号 | 含义 |
|---|---|
| `B` | 训练 batch 中的序列条数，也可以理解为有多少段 16 帧样本 |
| `L` | LSTM 时间步，训练时 `L=16`，推理时 `L=1` |
| `B*L` | 被展平成逐帧处理后的 batch 大小 |
| `N` | 推理时一次传入的观测数，通常是 1 |
| `DIM_ALL` | 完整观测维度，当前为 4078 |
| `DIM_ENTITY` | 实体特征维度，当前为 3935 |
| `DIM_TACTIC` | 战术上下文特征维度，当前为 143 |
| `LABEL_SIZE_LIST` | 模型动作输出分支维度，当前为 `[12, 16, 16, 16, 16, 9]` |
| `LEGAL_ACTION_SIZE_LIST` | 推理时原始合法动作 mask 的分支维度，当前为 `[12, 16, 16, 16, 16, 108]` |

注意：

- 模型输出 target 分支是 9 维。
- 环境给的原始 target 合法动作是 `12 * 9 = 108` 维。
- 这两个数不矛盾，因为 target 是否合法依赖第一维按钮动作。推理时先采样第 0 个动作分支，再从 `12 x 9` 的 target mask 中选出对应按钮的那一行，变成 9 维 target mask。

## 4. 从游戏状态到模型输入

模型本身只接收 `feature_vec`，并不直接处理环境原始字典。完整链路是：

```text
环境 observation
  -> Agent.observation_process()
  -> Info.update(observation)
  -> ObsBuilder.build_observation(info)
  -> feature_vec: np.ndarray, shape = [4078]
  -> Agent._model_inference()
  -> Model.forward()
```

### 4.1 `ObsBuilder.build_observation`

`feature/obs_builder.py` 中的 `build_observation()` 负责拼接观测。

它主要做这些事：

1. 从 `Info` 里取我方英雄、敌方英雄、我方小兵、敌方小兵、河蟹、我方塔、敌方塔、敌方子弹。
2. 分别调用 `process_hero`、`process_soldier`、`process_river_crab`、`process_sub_tower`、`process_bullets`。
3. 把所有实体特征拼成 `x_entity`，长度必须等于 3935。
4. 调用 `TacticContext.build_features(info)` 得到 `x_tactic`，长度必须等于 143。
5. 拼接成最终 `x = x_entity + x_tactic`，长度必须等于 4078。

最终断言：

```python
assert len(x_entity) == Args.DIM_ENTITY
assert x.shape[0] == Args.DIM_ALL
```

### 4.2 位置特征：125 维

所有单位和子弹都带位置特征。位置由 `process_position()` 编码成 125 维：

```text
DIM_DISTANCE = DIM_RELATIVE_DISTANCE + DIM_WHOLE_DISTANCE
             = 87 + 38
             = 125
```

相对位置部分 87 维：

- x 方向 bucket：43 维 one-hot。
- z 方向 bucket：43 维 one-hot。
- 相对距离比例：1 维连续值。

全局位置部分 38 维：

- x 方向全局 bucket：18 维 one-hot。
- z 方向全局 bucket：18 维 one-hot。
- x 格内比例：1 维连续值。
- z 格内比例：1 维连续值。

所以：

```text
43 + 43 + 1 + 18 + 18 + 1 + 1 = 125
```

如果目标不可见，位置特征会返回全 0。

### 4.3 单位公共特征：168 维

单位公共特征由 `process_unit()` 生成，适用于英雄、小兵、河蟹、防御塔。

结构是：

```text
单位公共特征 DIM_UNIT = 血量编码 + 印记编码 + 位置编码
```

具体为：

| 部分 | 维度 | 说明 |
|---|---:|---|
| 血量比例 | 1 | `hp / hp_max` |
| 血量 bucket | 26 | HP 上限 2400，每 100 一个单位，加边界 |
| 印记编码 | 16 | 鲁班和狄仁杰相关 mark 层数 |
| 位置编码 | 125 | 上一节的 `DIM_DISTANCE` |
| 合计 | 168 | `1+26+16+125` |

### 4.4 英雄特征：354 维

单个英雄特征 `DIM_HERO=354`。

结构可以拆成：

| 部分 | 维度 | 说明 |
|---|---:|---|
| 英雄身份 | 1 | 鲁班七号为 -1，狄仁杰为 1 |
| 行为 one-hot | 9 | 8 个已知行为加未知位 |
| 法力值 EP | 10 | EP 比例加 bucket |
| 5 个技能冷却 | 65 | 1/2/3 技能、召唤师技能、回复，每个 13 维 |
| 等级 | 15 | 1 到 15 级 one-hot |
| 金钱变化 | 18 | 金钱增量 bucket、是否自然增长、总金钱比例 |
| 是否在草丛 | 1 | 标量 |
| 防御塔相关 | 2 | 是否在塔攻击范围内、是否为塔目标 |
| buff 编码 | 65 | 已知 buff 加未知位 |
| 单位公共特征 | 168 | 血量、印记、位置 |
| 合计 | 354 | 上述相加 |

### 4.5 小兵特征：176 维

单个小兵特征 `DIM_SOLDIER=176`。

结构为：

| 部分 | 维度 | 说明 |
|---|---:|---|
| 行为 one-hot | 3 | `State_Dead`、`Attack_Path`、未知 |
| 小兵类型 | 3 | 近战、远程、炮车 |
| 塔相关 | 2 | 是否在塔攻击范围内、是否为塔攻击目标 |
| 单位公共特征 | 168 | 血量、印记、位置 |
| 合计 | 176 | `3+3+2+168` |

模型最多考虑我方 4 个小兵、敌方 4 个小兵。

```text
我方小兵: 4 * 176 = 704
敌方小兵: 4 * 176 = 704
```

我方小兵默认按距离排序，敌方小兵按 `runtime_id` 升序排序。这点很重要，因为敌方小兵还会进入 target 候选，如果排序和官方 target index 对不齐，target 头会把概率分配给错误目标。

### 4.6 河蟹特征：173 维

河蟹特征 `DIM_RIVER_CRAB=173`。

结构为：

```text
河蟹行为 one-hot 5 维 + 单位公共特征 168 维 = 173
```

如果河蟹不可见，则返回全 0 特征。

### 4.7 防御塔特征：173 维

单个防御塔特征 `DIM_ORGAN=173`。

结构为：

```text
塔目标/血包相关 5 维 + 单位公共特征 168 维 = 173
```

5 维里包含：

- 当前攻击目标类型。
- 塔后是否有血包。
- 血包生成剩余时间。

模型包含我方塔 1 个、敌方塔 1 个：

```text
我方塔: 173
敌方塔: 173
```

### 4.8 子弹特征：130 维

单个子弹特征 `DIM_BULLET=130`。

结构为：

```text
子弹来源技能 slot one-hot 5 维 + 位置编码 125 维 = 130
```

模型最多看 10 个子弹：

- 9 个最近的敌方英雄子弹。
- 1 个敌方防御塔子弹。

所以：

```text
DIM_BULLETS = 10 * 130 = 1300
```

### 4.9 实体特征总和

实体特征由这些部分拼接：

| 部分 | 维度 |
|---|---:|
| 我方英雄 | 354 |
| 敌方英雄 | 354 |
| 我方小兵 4 个 | 704 |
| 敌方小兵 4 个 | 704 |
| 河蟹 | 173 |
| 我方塔 | 173 |
| 敌方塔 | 173 |
| 敌方子弹 10 个 | 1300 |
| 合计 | 3935 |

对应公式：

```text
DIM_ALL_UNITS = DIM_HERO*2 + DIM_SOLDIERS*2 + DIM_RIVER_CRAB + DIM_ORGAN*2
              = 354*2 + 704*2 + 173 + 173*2
              = 2635

DIM_ENTITY = DIM_ALL_UNITS + DIM_BULLETS
           = 2635 + 1300
           = 3935
```

### 4.10 战术上下文特征：143 维

战术上下文由 `TacticContext.build_features()` 生成。它不是神经网络层，而是一组手工设计的高级状态摘要。

它把游戏局面提炼成九组特征：

1. 战斗状态：敌人是否可见、距离、双方血量、能不能打、狂暴状态。
2. 连招状态：英雄身份、连招阶段、上一帧动作、技能可用性、被动层数。
3. 兵线状态：敌我小兵数量、最近敌方小兵血量、是否可补刀、是否推进。
4. 河蟹状态：河蟹可见性、距离、血量、安全性。
5. 防御塔状态：塔下是否安全、敌塔当前打谁、是否有点塔窗口。
6. 恢复状态：低血低蓝、回复技能、回城、血包、安全回城窗口。
7. 攻击精度：近期普攻和技能命中率、连续空攻击次数。
8. 草丛伏击：是否在草、蹲草时间、伏击是否就绪、是否刚出草。
9. 鲁班大招风险：敌方鲁班大招是否存在、距离、危险范围、是否正在远离。

这些特征的意义是：让模型不必完全从底层实体坐标和状态里自己推导“现在是不是能打、是不是该推线、是不是该撤塔、是不是该吃血包”。这是一种明显的特征工程加神经网络结合的设计。

## 6. 网络中 MLP 的基本实现

项目里所有 MLP 都用同一个类：

```python
class MLP(nn.Module):
    def __init__(self, fc_feat_dim_list, name, non_linearity=nn.ReLU, non_linearity_last=False)
```

例如：

```python
MLP([143, 128, 64], "tactic_mlp")
```

会构建：

```text
Linear(143 -> 128)
ReLU
Linear(128 -> 64)
```

默认最后一层后面不加 ReLU。

如果 `non_linearity_last=True`，最后一层后也会加 ReLU。例如：

```python
MLP([480, 512], "concat_mlp", non_linearity_last=True)
```

会构建：

```text
Linear(480 -> 512)
ReLU
```

所有通过 `make_fc_layer()` 创建的线性层都会做：

```python
nn.init.orthogonal_(fc_layer.weight)
nn.init.zeros_(fc_layer.bias)
```

也就是说：

- Linear 权重用正交初始化。
- Linear bias 初始化为 0。
- LSTM 没有在代码中手动初始化，使用 PyTorch 默认初始化。

## 7. `process_sub_feature`：共享压缩位置和单位信息

这是理解模型结构的关键函数：

```python
def process_sub_feature(self, x, mlp, is_unit: bool):
```

它的目的：把每个实体里很长的位置和单位公共特征先压缩，再和实体专属特征拼起来送入对应 MLP。

### 7.1 对单位类实体的处理

单位类实体包括：

- 英雄。
- 小兵。
- 河蟹。
- 防御塔。

这些实体最后 168 维都是 `DIM_UNIT`，而 `DIM_UNIT` 的最后 125 维是位置。

当 `is_unit=True` 时：

```python
unit_no_pos = self.unit_no_pos_mlp(x[..., -Args.DIM_UNIT:-Args.DIM_DISTANCE])
pos = self.position_mlp(x[..., -Args.DIM_DISTANCE:])
ret[0] = x[..., :-Args.DIM_UNIT]
return mlp(torch.cat([实体专属特征, unit_no_pos, pos], dim=-1))
```

也就是：

```text
原始实体特征
  -> 实体专属前缀
  -> 单位公共非位置部分 43 维 -> unit_no_pos_mlp -> 32 维
  -> 位置部分 125 维 -> position_mlp -> 64 维
  -> 拼接后进入实体专属 MLP
```

其中：

```text
unit_no_pos_mlp: 43 -> 64 -> 32
position_mlp: 125 -> 128 -> 64
```

为什么单位公共非位置部分是 43 维？

```text
DIM_UNIT = 168
DIM_DISTANCE = 125
168 - 125 = 43
```

所以对任何单位，公共部分都会被压缩成：

```text
43 -> 32
125 -> 64
合计 96
```

这 96 维替代原始 168 维公共单位信息，减少了后续 MLP 的输入维度。

### 7.2 对子弹类实体的处理

子弹不是单位，没有血量、印记等 `DIM_UNIT` 信息，所以 `is_unit=False`。

子弹只有：

```text
slot 特征 5 维 + 位置特征 125 维 = 130
```

处理时：

```text
slot 前缀 5 维保留
位置 125 维 -> position_mlp -> 64 维
拼接成 69 维
送入 bullet_mlp
```

所以子弹 MLP 的输入不是 130，而是 69。

## 8. 各实体编码器

这一节按 `Model.__init__()` 中定义顺序讲每个编码器。

### 8.1 位置编码器 `position_mlp`

```python
fc_position_list = [Args.DIM_DISTANCE, 128, 64]
self.position_mlp = MLP(fc_position_list, "position_mlp")
```

结构：

```text
125 -> 128 -> 64
```

作用：

- 压缩位置编码。
- 被所有单位和子弹共享。

### 8.3 英雄编码器

定义：


先看输入维度。

单个英雄原始维度是 354。英雄最后 168 维是单位公共特征，其中：

- 位置 125 维压缩成 64 维。

- 前面共享层学习“英雄类实体通用表示”。

所以：

- 敌方英雄是 target 1。

## 10. target 候选 embedding

模型一共有 9 个 target 候选。它们不是直接从固定 one-hot 来的，而是从相关实体编码的 32 维表示里取出来。

target 候选列表：

| target id | 来源 | embedding 维度 | 说明 |
|---:|---|---:|---|
| 0 | 常量填充 | 32 | `0.1 * ones_like(...)`，通常可理解为空目标或默认目标 |
| 1 | 敌方英雄 | 32 | 敌方英雄 128 维输出的后 32 维 |
| 2 | 我方英雄 | 32 | 我方英雄 128 维输出的后 32 维 |
| 3 | 敌方小兵 1 | 32 | 第 1 个敌方小兵编码 |
| 4 | 敌方小兵 2 | 32 | 第 2 个敌方小兵编码 |
| 5 | 敌方小兵 3 | 32 | 第 3 个敌方小兵编码 |
| 6 | 敌方小兵 4 | 32 | 第 4 个敌方小兵编码 |
| 7 | 敌方防御塔 | 32 | 敌方塔编码 |
| 8 | 河蟹 | 32 | 河蟹编码 |

## 11. 公共主干的三条路径

实体 480 维向量和战术 143 维向量会进入三条路径：

1. LSTM 路径：学习时间信息。
2. MLP 旁路：学习当前帧即时信息。
3. 战术 MLP 路径：处理手工战术上下文。

### 11.1 LSTM 路径

先把 480 维实体摘要压成 512 维：

```python
self.concat_mlp = MLP([480, 512], "concat_mlp", non_linearity_last=True)
fc_public_result = self.concat_mlp(concat_result)
```

形状：

```text
concat_result: [B*L, 480]
fc_public_result: [B*L, 512]
```

训练时 `L=16`，所以 reshape 成：

```python
reshape_fc_public_result = fc_public_result.reshape(-1, self.lstm_time_steps, self.lstm_unit_size)
```

形状：

```text
训练: [B*16, 512] -> [B, 16, 512]
推理: [N*1, 512] -> [N, 1, 512]
```

LSTM 定义：

```python
self.lstm = torch.nn.LSTM(
    input_size=512,
    hidden_size=512,
    num_layers=1,
    bias=True,
    batch_first=True,
    dropout=0,
    bidirectional=False,
)
```

含义：

- 单层 LSTM。
- 输入维度 512。
- 隐状态维度 512。
- 非双向。
- `batch_first=True`，输入形状是 `[batch, time, feature]`。
- dropout 为 0。

初始状态：

```python
lstm_initial_state_in = [
    lstm_hidden_init.unsqueeze(0),  # [1, B, 512]
    lstm_cell_init.unsqueeze(0),    # [1, B, 512]
]
```

输出：

```text
lstm_outputs: [B, L, 512]
lstm_hidden_output: [1, B, 512]
lstm_cell_output: [1, B, 512]
```

然后把时间维重新展平：

```python
lstm_outputs = lstm_outputs.reshape(-1, 512)
```

形状：

```text
[B, L, 512] -> [B*L, 512]
```

### 11.2 MLP 旁路

旁路定义：

```python
self.concate_mlp_other = MLP([480, 512, 512], "concat_other_mlp")
```

结构：

```text
480 -> 512 -> 512
```

形状：

```text
concat_result: [B*L, 480]
public_mlp_result: [B*L, 512]
```

这条路径不经过 LSTM，所以它更像是“当前帧局面快速判断”。

为什么要有这条路？

- LSTM 可以记忆历史，但可能会压缩掉一些当前帧强信号。
- 旁路 MLP 直接看当前帧实体摘要，有利于保留即时局势。
- 最后把 LSTM 和旁路拼起来，让模型同时利用历史和当前。

### 11.3 战术特征路径

战术路径定义：

```python

```

结构：

```text

```

形状：

```text

tactic_result: [B*L, 64]
```

战术特征已经是比较高级的状态摘要，所以最后压到 64 维参与融合。

## 12. 三路融合成公共 512 维表示

三路输出是：


拼接后：

```python

```

融合 MLP：

```python

```

结构：

```text

```

最终公共表示：

```text
reshape_lstm_outputs_result: [B*L, 512]
```

这个 512 维向量同时喂给：

- 前 5 个动作头。
- target 动作头。
- value 价值头。

## 13. Actor：前 5 个普通动作头

定义：

```python
self.label_mlp = ModuleDict(
    {
        f"hero_label{label_index}_mlp": MLP(
            [self.dim_public, self.label_size_list[label_index]],
            f"hero_label{label_index}_mlp",
        )
        for label_index in range(len(self.label_size_list) - 1)
    }
)
```

由于 `LABEL_SIZE_LIST=[12,16,16,16,16,9]`，这里创建的是前 5 个动作头：

| 动作头 | 输出维度 | 结构 |
|---|---:|---|
| `hero_label0_mlp` | 12 | `512 -> 12` |
| `hero_label1_mlp` | 16 | `512 -> 16` |
| `hero_label2_mlp` | 16 | `512 -> 16` |
| `hero_label3_mlp` | 16 | `512 -> 16` |
| `hero_label4_mlp` | 16 | `512 -> 16` |

这些头输出的是 logits，不经过 softmax。

原因：

- 训练时 `compute_loss()` 会结合合法动作 mask 自己做 masked softmax。
- 推理时 `Agent._legal_soft_max()` 会结合环境给的 legal_action 自己做 masked softmax。

输出形状：

```text
label0: [B*L, 12]
label1: [B*L, 16]
label2: [B*L, 16]
label3: [B*L, 16]
label4: [B*L, 16]
```

## 14. Actor：最后一个 target 动作头

target 头是这个模型里最特别的一部分。它不是简单的 `Linear(512 -> 9)`，而是用 target embedding 和当前公共状态计算出来。

### 14.1 从公共状态生成 value 向量

代码：

```python
lstm_tar_embed_result = self.lstm_tar_embed_mlp(reshape_lstm_outputs_result)
reshape_label_result = lstm_tar_embed_result.reshape(-1, self.target_embed_dim, 1)
```

其中：

```python
self.lstm_tar_embed_mlp = make_fc_layer(512, 32)
```

形状：

```text
公共状态: [B*L, 512]
状态 target value: [B*L, 32]
reshape: [B*L, 32, 1]
```

这里代码注释把它称为 attention 中的 value。

### 14.2 从候选目标生成 query 权重

代码：

```python
ulti_tar_embedding = self.target_embed_mlp(tar_embedding)
ulti_tar_embedding = nn.functional.softmax(ulti_tar_embedding, dim=-1)
```

其中：

```python
self.target_embed_mlp = make_fc_layer(32, 32, use_bias=False)
```

形状：

```text
tar_embedding: [B*L, 9, 32]
target_embed_mlp 后: [B*L, 9, 32]
softmax 后: [B*L, 9, 32]
```

softmax 是对最后一维做的，也就是每个候选 target 的 32 维内部权重归一化。

### 14.3 矩阵乘法得到 9 个 target logits

代码：

```python
label_result = torch.matmul(ulti_tar_embedding, reshape_label_result)
```

形状：

```text
ulti_tar_embedding: [B*L, 9, 32]
reshape_label_result: [B*L, 32, 1]
matmul 输出: [B*L, 9, 1]
reshape: [B*L, 9]
```

这个结果就是最后一个动作分支的 logits。

直观理解：

- 每个 target 都有一个 32 维表示。
- 当前局面也被映射成一个 32 维状态向量。
- 每个 target 用自己的 32 维 query 权重和状态向量做匹配。
- 匹配分数就是 target logit。

虽然代码注释写的是“自注意力”，但从实现看，它更像是“target-conditioned scoring”：

```text
target_logit_i = softmax(W_target * target_embed_i) dot (W_state * public_state)
```

它不是标准 Transformer 那种 Q-K-V 多头注意力，因为这里没有显式 key，也没有多个 token 间的互相注意。

### 14.4 target 头的好处

相比直接 `Linear(512 -> 9)`，这种设计有几个好处：

- target 分数和实体编码绑定，敌方英雄、小兵、塔、河蟹的状态会直接影响 target 选择。
- 敌方小兵的 target 表示来自每个小兵自己的编码，不是固定编号的静态参数。
- 当某个目标不可见或特征全 0 时，它的 target embedding 会自然不同。
- 公共状态提供“我现在想做什么”，target embedding 提供“每个目标是什么”。

## 15. Critic：价值头

价值头定义：

```python
self.value_mlp = MLP([512, 64, 1], "hero_value_mlp")
```

结构：

```text
512 -> 64 -> 1
```

输出：

```text
value_result: [B*L, 1]
```

含义：

- 这是当前状态价值估计 `V(s)`。
- 它不是动作价值 `Q(s,a)`。
- 它用于 GAE 计算和 value loss。

训练中 value loss：

```python
self.value_cost = 0.5 * mean((reward_sum - value)^2)
```

其中 `reward_sum` 是 GAE 算出来的 value target。

## 17. logits、合法动作和采样

模型只输出 logits，不直接输出最终动作。最终动作由 `Agent._sample_masked_action()` 生成。

### 17.1 模型输出 logits 是 85 维

模型最终拼接：

```python
logits = torch.flatten(torch.cat(result_list[:-1], 1), start_dim=1)
```

维度：

```text
12 + 16 + 16 + 16 + 16 + 9 = 85
```

这 85 维对应：

| 分支 | 维度 |
|---|---:|
| action/button 分支 | 12 |
| 方向或参数分支 1 | 16 |
| 方向或参数分支 2 | 16 |
| 方向或参数分支 3 | 16 |
| 方向或参数分支 4 | 16 |
| target 分支 | 9 |

### 17.2 环境原始 legal_action 是 184 维

`Info` 里有注释说明原始 legal action：

```text
12 + 16*4 + 12*9
```

也就是：

```text
12 + 64 + 108 = 184
```

为什么最后是 108？

因为 target 合法性依赖第一个动作分支。

例如：

- 如果第一个分支选择“普攻”，合法 target 可能是敌方英雄、小兵、塔、河蟹。
- 如果第一个分支选择“移动”，target 可能没有意义。
- 如果第一个分支选择“回复”，target 也可能没有意义。

所以环境给的是一个矩阵：

```text
target_legal_action_o: [12, 9]
```

含义：

```text
对于每个 button/action，分别给出 9 个 target 是否合法。
```

### 17.3 推理时如何从 184 维 legal_action 变成 9 维 target mask

`Agent._sample_masked_action()` 逻辑：

1. 按 `[12,16,16,16,16]` 切前 5 个动作分支。
2. 对前 5 个分支分别做 masked softmax。
3. 先采样第 0 个动作分支，也就是 button/action。
4. 把原始 target mask reshape 为 `[12,9]`。
5. 用第 0 个动作分支的采样结果选出对应行，得到 9 维 target mask。
6. 再对模型输出的 9 维 target logits 做 masked softmax。
7. 采样最终 target。

核心代码：

```python
target_legal_action_o = np.reshape(
    legal_actions[index],
    [
        self.legal_action_size[0],
        self.legal_action_size[-1] // self.legal_action_size[0],
    ],
)
one_hot_actions = np.eye(self.label_size_list[0])[action_list[0]]
target_legal_action = np.sum(target_legal_action_o * one_hot_actions, axis=0)
```

其中：

```text
self.legal_action_size[0] = 12
self.legal_action_size[-1] = 108
108 / 12 = 9
```

### 17.4 训练样本里 legal_action 为什么是 85 维

训练样本不是保存环境原始 184 维 legal_action，而是保存裁剪后的 85 维。

在 `feature/definition.py`：

```python
def _update_legal_action(original_la, action):
    target_size = Config.LABEL_SIZE_LIST[-1]  # 9
    top_size = Config.LABEL_SIZE_LIST[0]      # 12
    fix_part = original_la[: -target_size * top_size]
    target_la = original_la[-target_size * top_size :]
    target_la = target_la.reshape([top_size, target_size])[action[0]]
    return np.concatenate([fix_part, target_la], axis=0)
```

也就是说：

```text
原始 legal_action:
12 + 16 + 16 + 16 + 16 + 108 = 184

训练保存 legal_action:
12 + 16 + 16 + 16 + 16 + 9 = 85
```

这和模型输出 85 维 logits 正好对齐。

## 18. masked softmax 的实现

推理时 softmax 在 `Agent._legal_soft_max()`：

```python
tmp = input_hidden - 1e20 * (1.0 - legal_action)
tmp_max = np.max(tmp, keepdims=True)
tmp = np.clip(tmp - tmp_max, -1e20, 1)
tmp = (np.exp(tmp) + 1e-5) * legal_action
probs = tmp / np.sum(tmp, keepdims=True)
```

作用：

- 非法动作会减去一个巨大值。
- 再做指数和归一化。
- 最后乘以 `legal_action`，保证非法动作概率为 0。
- `1e-5` 防止合法动作概率变成完全 0。

训练时 `compute_loss()` 里也做类似 masked softmax：

```python
legal_action_flag_list_max_mask = (1 - legal_action_flag_list[task_index]) * boundary
label_logits_subtract_max = label_result[task_index] - max(label_result[task_index] - mask)
label_exp_logits = legal_action_flag * exp(label_logits_subtract_max) + self.min_policy
label_probability = label_exp_logits / sum(label_exp_logits)
```

细节：

- 训练里 `MIN_POLICY=1e-5` 是加在 `legal * exp(...)` 后面的。
- 因此非法动作也会得到极小正数概率。
- 但真实采样动作来自合法动作，policy loss 取的是已采样动作的概率。
- entropy 计算时又乘了 legal mask。

这是一种数值稳定和防止 log(0) 的实现方式。

## 20. GAE 和 value target

`FrameCollector._calc_reward()` 负责计算 advantage 和 reward_sum。

核心公式：

```python
delta = -rl_info.value + rl_info.reward + gamma * rl_info.next_value
gae = gae * gamma * lamda + delta
rl_info.advantage = gae
rl_info.reward_sum = gae + rl_info.value
```

数学形式：

```text
delta_t = r_t + gamma * V(s_{t+1}) - V(s_t)
GAE_t = delta_t + gamma * lambda * GAE_{t+1}
reward_sum_t = GAE_t + V(s_t)
```

这里：

- `advantage` 用于 policy loss。
- `reward_sum` 用于 value loss。
- `gamma=0.995`。
- `lambda=0.95`。

## 21. PPO loss 详解

训练 loss 在 `Model.compute_loss()`。

总 loss：

```python
self.loss = self.value_cost + self.policy_cost + self.var_beta * self.entropy_cost
```

当前：

```text
var_beta = BETA_START = 0
```

所以实际参与优化的是：

```text
loss = value_cost + policy_cost
```

熵项会计算，但因为系数为 0，默认不影响参数更新。

### 21.1 value loss

代码：

```python
fc2_value_result_squeezed = value_result.squeeze(dim=1)
self.value_cost = 0.5 * torch.mean(torch.square(reward - fc2_value_result_squeezed), dim=0)
```

含义：

```text
value_cost = 0.5 * mean((reward_sum - V(s))^2)
```

这是 critic 的均方误差。

### 21.2 policy loss

对每个动作分支都计算 PPO clipped loss。

当前 6 个分支都参与强化学习：

```python
IS_REINFORCE_TASK_LIST = [True, True, True, True, True, True]
```

每个分支流程：

1. 取当前模型 logits。
2. 结合 legal_action mask 得到当前策略概率 `label_probability`。
3. 用 one-hot action 取出实际动作概率 `policy_p`。
4. 从样本里取旧策略概率 `old_policy_p`。
5. 计算 ratio。
6. 用 PPO clipped objective。
7. 乘该分支 weight。
8. 加到总 policy loss。

关键代码：

```python
policy_p = (one_hot_actions * label_probability).sum(1)
policy_log_p = torch.log(policy_p + epsilon)

old_policy_p = (one_hot_actions * old_label_probability_list[task_index] + epsilon).sum(1)
old_policy_log_p = torch.log(old_policy_p)

final_log_p = policy_log_p - old_policy_log_p
ratio = torch.exp(final_log_p)

surr1 = ratio.clamp(0.0, 3.0) * advantage
surr2 = ratio.clamp(1.0 - clip_param, 1.0 + clip_param) * advantage

temp_policy_loss = -weighted_mean(min(surr1, surr2))
```

当前 `clip_param=0.2`，所以：

```text
surr2 ratio clip 范围 = [0.8, 1.2]
```

注意一个实现细节：

- `final_log_p` 在每个 task 内部重置为 0。
- 因此这里是对 6 个动作分支分别算 PPO loss 再相加。
- 它不是把 6 个分支的 log probability 加起来形成一个完整 joint action probability 再算一次 PPO。

这样做的含义：

- 每个动作头都用同一个 advantage 监督。
- 每个动作头有自己的旧概率和当前概率。
- 分支之间的 credit assignment 更简单，但没有显式建模联合动作概率。

### 21.3 weight/sub_action

`compute_loss()` 里的：

```python
usq_weight_list = data_list[3 + 2 * len(label_size_list) : 3 + 3 * len(label_size_list)]
```

实际对应样本里的 6 个 `sub_action` 或分支权重。

它们用于：

```python
temp_policy_loss = -sum(objective * weight) / max(sum(weight), 1)
```

作用：

- 某些动作分支在某些主动作下可能没有意义。
- weight 可以让这些分支不参与或少参与 loss。

### 21.4 entropy loss

代码先计算 entropy：

```python
temp_entropy_loss = -sum(p * legal * log(p))
```

然后又取负的加权平均：

```python
temp_entropy_loss = -weighted_mean(temp_entropy_loss)
```

所以 `entropy_cost` 实际是负熵。

总 loss 是：

```python
loss = value_cost + policy_cost + beta * entropy_cost
```

如果 `beta > 0`，因为 `entropy_cost` 是负熵，优化时会倾向于增大策略熵，鼓励探索。

但当前 `beta=0`，所以熵项只是被计算和监控，不影响更新。

### 21.5 `is_train` 的细节

`compute_loss()` 里读取了：

```python
usq_is_train = data_list[-3]
frame_is_train = usq_is_train.squeeze(dim=1)
```

但当前函数后续没有使用 `frame_is_train`。

也就是说，在这份代码里，loss 的有效帧控制主要来自各动作分支的 `weight_list/sub_action`，而不是 `is_train` 这个字段本身。

这是阅读代码时容易忽略的细节。

## 23. 推理时 LSTM 状态如何连续

Agent 初始化和 reset 时：

```python
self.lstm_hidden = np.zeros([512])
self.lstm_cell = np.zeros([512])
```

每次推理：

```python
format_inputs = [feature_vec, lstm_hidden_state, lstm_cell_state]
output_list = self.model(format_inputs, inference=True)
logits, value, _lstm_cell, _lstm_hidden = output_list
```

模型返回新的：

```text
lstm_cell_output: [1, N, 512]
lstm_hidden_output: [1, N, 512]
```

Agent 会保存：

```python
self.lstm_cell = act_data.lstm_cell
self.lstm_hidden = act_data.lstm_hidden
```

下一帧继续作为初始状态输入模型。

这就是模型“记住上一些帧”的方式。

注意：

- 推理时 `lstm_time_steps=1`。
- 不是每次推理都把过去 16 帧重新输入。
- 历史信息存在 LSTM hidden/cell 里。

## 24. 训练时 LSTM 初始状态如何打包

`FrameCollector._format_data()` 每 16 帧组成一个样本。

关键逻辑：

```python
if cnt == self._LSTM_FRAME:
    cnt = 0
    sample = self._reshape_lstm_batch_sample(sample_batch, sample_lstm)
    self.m_replay_buffer[i].append(sample)
    sample_lstm = rl_info.lstm_info
```

含义：

- 每 16 帧形成一段序列。
- 这段序列还会带上一个 `sample_lstm`。
- `sample_lstm` 包含 LSTM cell 和 hidden，各 512 维。
- 下一段序列的初始 LSTM 状态来自上一段末尾保存的 `rl_info.lstm_info`。

这样 learner 训练时虽然每条样本只有 16 帧，但 LSTM 初始状态不是永远全 0，而是可以接续上一段 rollout 的状态。

## 25. 网络外的动作偏置

在 `Agent._model_inference()` 中，模型输出 logits 后并不是立刻采样，而是先调用：

```python
biased_logits = self._apply_combo_skill_bias(logits[i], legal_action[i])
```

这是一个网络外的人为策略偏置。

触发条件大致是：

- 能看到敌方英雄。
- 敌方活着。
- 敌人在 `SKILL_URGENCY_DISTANCE=8500` 范围内。
- 自己不在敌方活塔攻击范围内。
- 优先技能合法且可用。

优先技能：

```python
SKILL_BUTTON_PRIORITY = {
    112: [6, 4, 5],
    133: [6, 4],
}
```

也就是：

- 鲁班七号优先 3 技能、1 技能、2 技能。
- 狄仁杰优先 3 技能、1 技能。

偏置值：

```python
SKILL_BUTTON_LOGIT_BONUS = 2.4
SKILL_TARGET_LOGIT_BONUS = 1.2
```

如果触发：

- 给对应技能按钮 logit 加 2.4。
- 如果这个按钮指向敌方英雄 target 合法，则给 target 1 的 logit 加 1.2。

这个逻辑不是神经网络参数的一部分，不会在 `Model.forward()` 内出现。它是采样前对 logits 的人工修正。

## 26. 红蓝方动作方向翻转

`Agent.action_process()` 中有阵营方向处理：


## 29. 为什么这个网络这样设计

### 29.1 为什么不用 CNN

输入不是图像，而是结构化状态：

- 坐标被离散化和归一化。
- 血量、技能、buff、行为、塔状态都已经手工编码。
- 小兵、子弹数量也被固定上限和排序。

因此 CNN 没有明显合适的二维局部结构可利用。用 MLP 编码结构化实体更自然。

### 29.2 为什么要实体分组 MLP

如果直接把 4078 维全部丢进一个大 MLP，模型需要自己学习哪些维度属于英雄、哪些属于小兵、哪些属于子弹。

当前设计先按实体拆开：

- 英雄用英雄编码器。
- 小兵用小兵编码器。
- 塔用塔编码器。
- 子弹用子弹编码器。

这样网络结构本身就告诉模型“这些东西是同类实体”，减少学习难度。

### 29.3 为什么同类实体共享前几层

例如我方小兵和敌方小兵共享 `soldier_mlp`，最后才分 `soldier_frd_fc` 和 `soldier_emy_fc`。

好处：

- 小兵的基础属性处理方式相同。
- 共享参数减少参数量。
- 最后一层区分敌我语义。

英雄、塔、子弹都有类似设计。

### 29.4 为什么小兵和子弹用 max pooling

小兵最多 4 个，子弹最多 9 个。模型需要把可变数量实体压成固定维度。

这里采用 max pooling：

```text
[B*L, num_entities, feature_dim] -> max over num_entities -> [B*L, feature_dim]
```

含义：

- 对每个特征维度，保留最强响应。
- 不关心具体是第几个小兵触发了该响应。
- 简单、高效、固定输出维度。

缺点：

- 会丢失多个实体之间的数量和排列细节。
- 例如两个危险子弹和一个危险子弹，在 max pooling 下可能很像。

不过数量信息部分已经在观测和战术特征中有一定补充。

### 29.5 为什么有 LSTM

MOBA 对线不是单帧决策问题。

很多重要信息需要时间上下文：

- 敌方刚刚交过技能没有。
- 自己连招进行到哪一步。
- 是否正在远离鲁班大招。
- 攻击是否连续落空。
- 草丛伏击是否等待了一段时间。
- 兵线状态变化趋势。

虽然战术特征里已经保存了一部分历史统计，但 LSTM 可以学习更通用的时间模式。

### 29.6 为什么还有 MLP 旁路

只用 LSTM 可能让所有当前帧信息都通过 recurrent state 混合，当前强信号可能被压缩。

旁路 MLP 直接从当前帧 480 维实体摘要到 512 维，和 LSTM 输出拼接。

这相当于告诉模型：

```text
你既可以看历史，也可以直接看当前帧。
```

### 29.7 为什么加入战术上下文特征

战术特征是人为总结的高层信息。它把很多需要推理的内容直接喂给模型，例如：

- 现在能不能打。
- 有没有安全点塔窗口。
- 是否安全回城。
- 是否处在连招阶段。
- 鲁班大招是否危险。

这会让模型更容易学到合理策略，尤其在训练资源有限时很有帮助。

### 29.8 为什么 target 头要用实体 embedding

target 选择天然和实体状态相关。

如果直接输出 9 个 target logits，模型需要在公共状态里隐式记住所有 target 状态。

当前设计让 target logit 直接依赖对应实体 embedding：

```text
target 1 的分数来自敌方英雄 embedding
target 3 到 6 的分数来自敌方小兵 embedding
target 7 的分数来自敌方塔 embedding
target 8 的分数来自河蟹 embedding
```

这让 target 选择更贴近“目标本身是否值得选”。

## 30. 当前实现中容易混淆或需要注意的点

### 30.1 模型输出是 85 维，不是 184 维

推理时环境给的原始 legal_action 是 184 维，但模型 logits 是 85 维。

原因：

- 模型 target 头只输出 9 个 target 分数。
- 原始合法 target 是 `12 x 9`。
- 采样时先确定第 0 个动作分支，再选对应的 target mask 行。

### 30.2 训练样本里保存的是裁剪后的 legal_action

`_update_legal_action()` 会把原始 `12 x 9` target mask 根据实际 action[0] 裁剪成 9 维。

所以 learner 里看到的是：

```text
feature 4078 + legal_action 85
```

不是：

```text
feature 4078 + legal_action 184
```

### 30.3 target 0 是常量填充

代码里：

```python
tar_embed_0 = 0.1 * torch.ones_like(tar_embed_list[-1])
tar_embed_list.insert(0, tar_embed_0)
```

target 0 不是来自某个实体，而是常量 0.1 向量。

### 30.4 value 头和 policy 头共享主干

Actor 和 Critic 共用前面的所有实体编码器、LSTM、旁路、战术 MLP 和融合 MLP。

只有最后：

- policy 使用动作头。
- value 使用 `value_mlp`。

这是典型共享主干 Actor-Critic。

### 30.5 logits 没有 softmax

模型输出的动作结果是 logits。

softmax 发生在：

- 推理时：`Agent._legal_soft_max()`。
- 训练时：`Model.compute_loss()`。

这很重要，因为 softmax 必须结合 legal action mask。

### 30.6 `channels_last` 对这个模型意义不大

`Agent.__init__()` 中有：

```python
self.model = self.model.to(memory_format=torch.channels_last)
```

但当前网络主要是 Linear 和 LSTM，没有 Conv2D 图像张量。`channels_last` 对这类模型通常不会像 CNN 那样带来明显收益。

### 30.7 `frame_is_train` 当前没有进入 loss

代码读取了 `is_train`，但没有用它过滤 value loss 或 policy loss。

真正参与 policy loss 加权的是 `weight_list/sub_action`。

如果以后想严格过滤死亡帧或不可训练帧，需要检查并可能补上 `frame_is_train` mask。

### 30.8 熵项当前不影响训练

虽然代码计算了 entropy loss，但：

```python
BETA_START = 0
```

所以：

```text
loss = value_cost + policy_cost
```

如果要鼓励探索，可以考虑把 beta 调成正数，但这会改变训练行为。

### 30.9 网络外 combo bias 会改变采样分布

模型输出 logits 后，Agent 可能加技能连招偏置。

这个偏置不是网络参数，却会影响训练时采集到的 action 和 old probability。

如果分析纯模型能力，要区分：

- `Model.forward()` 原始策略。
- `Agent._apply_combo_skill_bias()` 后的行为策略。

### 30.10 target head 不是标准 Transformer attention

代码注释叫“自注意力”，但实现没有 key，也没有多头。

更准确的说法是：

```text
用目标 embedding 生成一组 32 维权重，
再和当前状态的 32 维向量做点积，
得到每个 target 的分数。
```

## 31. 修改网络时最容易牵动的地方

### 31.1 如果改观测维度

需要同步检查：

- `Args` 里的维度定义。
- `DimConfig` 里的拆分。
- `ObsBuilder.build_observation()` 的拼接顺序。
- `Model.forward()` 里的 split 顺序。
- `Config.SERI_VEC_SPLIT_SHAPE`。
- `Config.DATA_SPLIT_SHAPE` 和 `Config.data_shapes`。
- checkpoint 是否还能加载。

尤其是实体特征顺序不能随便改，因为模型按固定顺序 split。

### 31.2 如果改动作空间

需要同步检查：

- `Config.LABEL_SIZE_LIST`。
- `Config.LEGAL_ACTION_SIZE_LIST`。
- `Agent._sample_masked_action()`。
- `feature/definition.py::_update_legal_action()`。
- `Config.DATA_SPLIT_SHAPE`。
- `Config.data_shapes`。
- `Model.label_mlp` 和 target 头。
- 环境返回的 `legal_action` 和 `sub_action_mask`。

最容易出错的是最后 target 分支，因为它涉及：

```text
模型输出 9
环境原始合法动作 12*9
训练样本裁剪后 9
```

### 31.3 如果增加 target 候选

需要同步：

- `LABEL_SIZE_LIST[-1]`。
- target embedding 列表 `tar_embed_list`。
- 环境 legal action 的 target 矩阵宽度。
- `_update_legal_action()`。
- `Agent._sample_masked_action()`。
- 所有概率和样本 shape。

### 31.4 如果改 LSTM 长度

需要同步：

- `Config.LSTM_TIME_STEPS`。
- `Config.data_shapes`。
- `Config.SAMPLE_DIM` 会自动按公式变，但前提是 `data_shapes` 正确。
- `FrameCollector._reshape_lstm_batch_sample()`。
- 训练样本池里旧样本可能不兼容。

### 31.5 如果想换成 GRU 或 Transformer

要注意：

- 当前接口需要传入 `lstm_hidden` 和 `lstm_cell`。
- GRU 只有 hidden，没有 cell，所以 Agent、Sample、FrameCollector、Config 里的 LSTM state 结构都要改。
- Transformer 如果想用过去帧，需要保存序列或缓存，不再是简单 hidden/cell。
- 现有训练样本是每 16 帧加一个初始 recurrent state，适合 LSTM/GRU，不直接适合完整 Transformer 记忆。

## 34. 最终总结

这套神经网络的本质是：

```text
结构化特征工程 + 实体分组 MLP 编码 + LSTM 时序记忆 + MLP 当前帧旁路 + 战术上下文辅助 + PPO Actor-Critic
```

它不是一个端到端从像素学操作的模型，而是一个非常明确地利用 MOBA 领域结构的策略网络。

最核心的三个设计点：

1. 实体拆分编码：英雄、小兵、塔、河蟹、子弹分别处理，再融合。
2. 时序加旁路：LSTM 负责历史，MLP 旁路负责当前帧。
3. target attention：目标选择不是固定线性头，而是用目标实体 embedding 和当前状态匹配得到。

最容易混淆的三个点：

1. 模型输出 85 维，但环境原始 legal_action 是 184 维。
2. target 头输出 9 维，推理时 target mask 从 `12 x 9` 中按第一个动作分支选择一行。
3. 训练样本保存的是裁剪后的 85 维 legal_action，而不是环境原始 184 维 legal_action。

如果只记一条主线：

```text
4078 维观测
  -> 实体 3935 + 战术 143
  -> 实体编码成 480
  -> LSTM 512 + 旁路 512 + 战术 64
  -> 融合成 512
  -> 输出 85 维策略 logits 和 1 维 value
```
